# Общая обработка caster/target для навыков

## Контекст проблемы

Некорректная работа навыков на технике, питомцах и маунтах была вызвана не отдельным ID навыка, а смешением ролей в серверной обработке `CSStartSkillPacket`.

В пакете запуска клиент присылает:

- `SkillCaster` - объект, от имени которого клиент хочет запустить навык.
- `SkillCastTarget` - цель навыка.
- `SkillObject` - дополнительные данные позиции, предмета или области.

До исправления сервер во многих ветках использовал `skillCaster.ObjId` как авторитетный источник. Это приводило к двум классам ошибок:

- персонаж верхом мог запускать обычные навыки через ветку mount-обработки;
- клиентский `ObjId` техники/питомца мог стать физическим кастером без проверки связи с игроком;
- self/source навыки могли получать цель из клиентского пакета, хотя по шаблону цель должна быть самим источником;
- rider/operator навыки, связанные с mount skill, могли исполняться с физическим кастером техники, хотя логическим кастером должен быть персонаж.

Для навыка автоматического полива это проявлялось особенно заметно: физический источник должен быть трактор/цистерна, а инициатором действия и владельцем игрового контекста остается водитель. Но это частный симптом общей ошибки.

## Новый общий слой

Добавлен `SkillContextResolver` в `AAEmu.Game/Models/Game/Skills/Resolvers`.

Resolver выполняет серверное разрешение контекста до выбора ветки выполнения навыка:

- определяет effective caster по серверному состоянию персонажа;
- для `SourceMount` и `SkillCasterType.Mount` берет attached unit из transform-chain персонажа;
- не доверяет клиентскому `ObjId`, если объект не контролируется игроком;
- нормализует цель для `TargetSelection.Source` и `TargetType.Self`;
- для `TargetType.Parent` поднимается к корневому родителю вложенной техники;
- строит цель rider/operator навыка так, чтобы source/self указывал на персонажа, а не на транспорт.

Проверка контроля сейчас учитывает:

- самого персонажа;
- активного `Mate` по владельцу или пассажирскому месту;
- `Slave` по владельцу, summoner или attached characters;
- transform parent-chain персонажа.

## Изменения в запуске навыков

`CSStartSkillPacket` теперь получает шаблон навыка и вызывает resolver до логики выполнения. После этого ветки работают с уже нормализованными `caster` и `target`.

Важное изменение в маршрутизации:

- mounted-ветка используется только для mount-context навыков: `SourceMount` или `SkillCasterType.Mount`;
- обычные common/learned навыки персонажа верхом больше не перехватываются общей mounted-веткой;
- pet/mount навыки вне посадки требуют, чтобы объект был контролируемым игроком;
- rider/operator skill исполняется с `player` как логическим кастером.

Существующий data-driven слой навыков не заменен частными условиями. Никакие ID навыков, ID воды или фиксированные затраты не добавлялись в код.

## Рефакторинг `CSStartSkillPacket`

Пакет запуска навыка разделен на несколько последовательных этапов, чтобы логика была ближе к рабочей схеме reference-проекта и легче проверялась:

- `TryReadRequest`, `TryReadCaster`, `TryReadTarget`, `TryReadObject` отвечают только за безопасное чтение клиентского пакета;
- `SkillContextResolver.AuthoritativeResolve` приводит caster/target к серверному состоянию до выполнения навыка;
- `ResolveExecutionMode` выбирает общий режим запуска без условий по ID навыков;
- `HandleMountedSkill`, `HandlePetSkill`, `HandleItemSkill`, `HandleLearnedSkill` и другие обработчики выполняют только свою ветку;
- `HandleSkillResult` централизует отправку ошибок и achievement-события.

Такой порядок делает пакет запуска навыка не точкой набора частных исправлений, а маршрутизатором в общую skill-систему. Специальная логика дисмаунта оставлена отдельным legacy-обработчиком, потому что она уже существовала и относится к состоянию привязки техники, а не к конкретному боевому или хозяйственному навыку.

## Влияние на ресурсы и баланс

Списание предметов, очков работы, реагентов и продуктов остается в шаблонах навыков, эффектах и item-handlers. Это важно для баланса: тысячи навыков должны управляться данными, а не ветками по ID.

Исправление меняет только контекст, в котором эти правила применяются:

- требования source/target проверяются относительно правильного физического источника;
- self/source эффекты получают корректную цель;
- связанные rider/operator эффекты получают персонажа как владельца действия;
- попытки подменить кастера клиентским `ObjId` отсекаются до применения эффектов.

Если конкретный навык должен тратить 10 единиц воды и 10 LP, это должно быть выражено в данных навыка, эффектах, реагентах или существующем обработчике контейнера/предмета. Код resolver не должен знать о таком ID.

## Сохранение состояния

Resolver не меняет persistent state напрямую. Он не списывает предметы, не меняет LP, не сохраняет технику и не пишет в БД. Состояние меняют только уже существующие системы:

- `Skill.Use` и последующие эффекты;
- item consumption через inventory/container;
- labor consumption в завершении навыка;
- save-логика объектов, если эффект меняет persistent-состояние.

Это снижает риск частичных списаний: resolver только приводит входные данные к серверной правде, а мутации остаются в местах, где уже есть packet/update/save протоколы.

## Покрытие тестами

Добавлены xUnit-тесты для общего resolver:

- `SourceMount` навык использует attached unit как caster и self/source target;
- обычный self-навык персонажа верхом сохраняет персонажа как caster/target;
- клиентская подмена чужого caster ObjId игнорируется для mounted source;
- `TargetType.Parent` выбирает root parent вложенной техники;
- rider self/source target указывает на персонажа;
- проверка контроля принимает attached slave и отклоняет чужой mate.

Тесты не завязаны на ID конкретного навыка.
